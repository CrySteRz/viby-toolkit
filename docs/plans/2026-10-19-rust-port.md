# Plan: viby-toolkit in Rust, no TypeScript

Status: proposed 2026-10-19, waiting for the owner's go-ahead.

## Goal and decisions

Owner, 2026-10-19:
- **Scope:** everything. All 57 `.ts` files, about 17,900 lines, become Rust:
  - the browser MCP server, native host and installer
  - the agentgrep server
  - the shared MCP loop and `lib/strip-noncode`
  - all 19 skill checkers
  - the statusline and the format hook
  - `tools/`, the test runner and every test
- **Install:** easy, and doable entirely by Claude. The person never runs a command.
- **agentgrep:** built in, linking the `agentgrep` crate at tag v0.1.7 as jcode does. Nothing
  routes agents to it, because the 2026-10-19 measurement showed no saving.

Stays as it is:
- the browser extension (JavaScript that runs inside the browser)
- `tests/routing/` (Python that drives `claude -p`)
- `hooks/session-start.sh` (plain `sh` that `cat`s JSON; a binary would only make it slower)

Version 3.0.0: how the plugin runs changes for everyone.

## How it is laid out

One binary, `viby`, with subcommands. One download per platform means one checksum to verify
and one cache entry per version.

```
Cargo.toml                       workspace (members: crates/viby, xtask)
rust-toolchain.toml              pinned stable
crates/viby/src/
  main.rs                        subcommand dispatch (one match; owned by T0)
  lib.rs                         module tree, so tests call functions directly
  core/{strip.rs,git.rs,args.rs} shared by the checkers (each checker keeps its own output format)
  mcp.rs                         stdio JSON-RPC loop (one tool per server)
  checks/<name>.rs               one file per checker (19)
  hooks/{statusline.rs,format.rs}
  browser/{protocol,host,install,actions,server}.rs
  agentgrep.rs
crates/viby/tests/<name>.rs      ported node:test suites, one file per suite
xtask/                           `cargo xtask check` (replaces run-all, check-references,
                                 check-version) and `cargo xtask parity`
plugins/viby-toolkit/bin/
  viby                           POSIX sh launcher
  viby.cmd                       Windows launcher, calls viby.ps1
  viby.ps1
  checksums.txt                  sha256 per target for this version, committed by the release
```

Subcommand names keep the scripts' names, so the docs change mechanically: `viby check-plan`,
`viby scan-test-quality`, `viby detect-stack`, `viby statusline`, `viby browser-server`,
`viby browser-host`, `viby agentgrep-server`, `viby host-port`. Each keeps its old contract:
the same arguments, `--json` and `--quiet`, exit 0 for clean, 1 for findings, 2 for nothing to
check, and the same output text.

Dependencies, kept small: `serde`/`serde_json`, `regex` plus `fancy-regex` (only for the two
lookbehind patterns, `check-test-drift.ts:103-106` and `check-agents.ts:138`), `agentgrep`
(git tag v0.1.7), `tempfile` (dev only). No async runtime: the MCP servers use threads, as the
TS ones used concurrent promises. No clap: a ~60-line argument parser in `core/args.rs` matches
`parseArgs` exactly.

## Install: what happens on a machine that has never seen it

`bin/viby` (and `viby.cmd` on Windows) runs on every call. It costs one `sh` process plus one
file-existence check:

1. If `$CLAUDE_PLUGIN_DATA/bin/<version>/viby` exists, `exec` it. The fallback directory is
   `~/.viby/bin/<version>/`, because the Bash tool does not get `CLAUDE_PLUGIN_DATA`. The version
   comes from `plugin.json`, read once and cached.
2. Otherwise, download `viby-<target>.tar.gz` (`.zip` on Windows) from the GitHub Release
   `v<version>` with `curl` (PowerShell `Invoke-WebRequest` on Windows). Check its SHA-256
   against `bin/checksums.txt` in the plugin, not against a file in the release, so a swapped
   asset is caught. On macOS, run `codesign --force --sign -` when the ad-hoc signature is
   missing. Unpack it into a temporary folder and rename it into place, so two sessions racing
   never run a half-written file.
3. No asset for this target, or no network: `cargo build --release --locked` from the plugin's
   own source into the data directory, about 1–2 minutes and only once.
4. No cargo either: print one line Claude can act on: `viby needs Rust: run
   curl --proto '=https' -sSf https://sh.rustup.rs | sh -s -- -y, then retry`, with the
   `winget install Rustlang.Rustup` equivalent on Windows. Exit 0 for the statusline (it prints
   `viby-toolkit`, as it does today on any error) and 1 elsewhere.

Targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-musl`,
`aarch64-unknown-linux-musl`, `x86_64-pc-windows-msvc`. musl builds are static, so they run on
any Linux.

## Updates (owner, 2026-10-19: "make sure viby is autoupdatable as well")

- **The binary follows the plugin.** The launcher keys its cache on the version in `plugin.json`.
  When Claude Code updates the plugin, the next call finds no binary for the new version and
  downloads and verifies it as above. It then deletes cached versions older than the previous
  one, keeping the previous one so a running session is not disturbed.
- **The browser host follows the binary.** The browser starts the host itself, outside Claude,
  from `~/.viby/browser/`. As today (`ensureInstalled`, `syncExtension`), the first browser call
  after an update copies the new host binary there and has the extension reload itself.
- **The plugin itself** arrives through Claude Code's marketplace auto-update. T15 checks
  whether a third-party marketplace auto-updates by default. If it does not, `install.sh`
  enables it, and the README says how to switch it off.
- Verified in T17: install 3.0.0-rc.1, publish rc.2, update the plugin, and confirm that the
  next skill call, the statusline and the browser all run rc.2, with no command from the person.

`hooks/run.sh` stays as a one-line `exec "$(dirname "$0")/../bin/viby" "$@"`, mapping an old
`.ts` path argument to its subcommand. Old installs and the README's statusline line therefore
keep working through 3.x.

## Sequence and why

T0 first: it owns the two hub files (`main.rs` dispatch, `checks/mod.rs`) and stubs every
module, so T3–T11 each own only their own files and can run in parallel. T1 comes before the
six checkers that use strip-noncode. T13 parity before T14 and T15, because the TypeScript is
the oracle and must still be there. Nothing is deleted until T17 has passed on the real released
binaries.

Execution: T3–T11 are independent implementer jobs, one per task, with writes confined to the
files they own. The main thread reviews each diff and runs its verify command. The main thread
does T0, T12–T18 itself.

## The risky steps and how each is de-risked

1. **Behavioural drift in the checkers.** 19 regex-heavy scripts are easy to port "nearly
   right". De-risk: T13 runs the TS and the Rust version of every checker on the same corpora
   (this repo, viby, viby-flow, viby-shot, and each test suite's fixtures), with `--json`, and
   diffs. Zero diffs is the bar; every intended difference is listed in the plan. JS regex
   semantics that differ (`\s`, `\b` on Unicode, the `/m` and `/g` loops) are the usual cause.
2. **strip-noncode offsets.** JS indexes by UTF-16 units, Rust by bytes. Every caller that
   reports a column must convert. Golden tests in T1 cover non-ASCII lines (`—`, `·`, emoji).
3. **The launcher on a fresh machine and on Windows.** T17 runs it with an empty data
   directory on macOS arm64 (this Mac) and on the CI's Linux and Windows runners: the download
   and verify path, a corrupted asset (it must refuse), no network (cargo fallback), and no
   cargo (the one-line message).
4. **Browser parity.** The native host is the riskiest Rust: framing, unix socket and named
   pipe, socket takeover. The 48 contract tests move over, and the 67-step live Brave run is
   repeated against `viby browser-server`.
5. **agentgrep as a crate.** Its library API (`run_grep`, `run_smart`, the render functions,
   the context struct) is what jcode calls. If the crate does not build on a target (musl,
   Windows), T11 falls back to shelling out for that target only and the release notes say so.

## Verification

- `cargo xtask check` replaces `npm run check`. It runs:
  - every suite, each with a minimum-pass count
  - `claude plugin validate .`
  - references, version and the SessionStart JSON check
  - `cargo clippy -D warnings`
  - the scanner on its own tests
- Live, from the released binaries:
  - Brave 67/67, plus `parallel` 2/2
  - agentgrep 14/14 and the install-guide step (now: binary missing, then download)
  - a real `claude -p` session with both servers
  - the statusline rendering in a real session
  - one skill per checker family run the way a skill runs it
- Fresh-machine install on macOS, Linux and Windows, as in risky step 3.

## Not doing

- The browser extension (JavaScript, runs in the browser) and `tests/routing` (Python).
- Rewriting skill prose beyond the command lines.
- Routing agents to agentgrep.
- Code-signing or notarizing with a paid certificate:
  - On macOS, curl downloads carry no quarantine flag and the binary gets an ad-hoc signature.
  - On Windows, SmartScreen's behaviour for script-downloaded CLI binaries is unverified, and T17 checks it.

## Rejected

- **Committing binaries to git.** Tens of MB per release, forever, in every clone.
- **Building with cargo on first use only.** Every machine would need Rust plus 1–2 minutes; it
  stays as the fallback.
- **One crate per checker.** 19 manifests for code that shares four helpers; modules in one
  crate give the same isolation for parallel work.
- **A SessionStart hook that downloads.** It cannot hold the MCP servers back until the
  download ends; the launcher on each call can.
- **cargo-dist.** Its own docs say its installers' checksum checks are "still a work in
  progress", and its installer does not pin checksums in our repo; a 40-line workflow does.
